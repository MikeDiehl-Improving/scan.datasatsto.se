Preserve the scanner-setup endpoints in server.js:

`GET /setup`:
- If `req.query.id` is present, it executes `Scan.Get_Codes` with that numeric ID and builds an HTML `codes` string, one `<span class="code" ...>` per row of `item.ReferenceCode` from the recordset (HTML-escaped via `simpleHtmlEncode`, which only escapes `&`, `<`, `>`). If the recordset is empty, `codes` stays an empty string, which is falsy, so the handler responds HTTP 500 with the `assets/error.html` page and message "That code didn't look right." If the recordset has at least one row, it responds HTTP 200 with the `assets/select-code.html` page containing that `codes` HTML.
- If `req.query.id` is absent, it sets `req.session.dummy = Date.now()` (keeps the session alive) and responds HTTP 200 with the `assets/setup.html` page, whose `Code` template value is `req.session.vendorCode || ""` (empty when no session vendor code is set yet, or the previously-stored session code when one exists).

`POST /setup`: unconditionally sets `req.session.vendorCode = req.body.code` (no validation of the value) and responds HTTP 200 with the `assets/ok.html` page showing that code.

Known defect to document but NOT exercise in automated HTTP tests (same class of issue verified in the `scan-recording` and `batch-random-id-generation`/random-scan-lookup features — it would crash the test process rather than produce a clean response): in the `GET /setup?id=...` branch, `recordset.forEach(...)` is called with no guard. If the underlying SQL statement itself fails, `sqlQuery`'s completion callback is invoked with `recordset === undefined` (the same swallowed-error mechanism used throughout this codebase), and `undefined.forEach` throws a `TypeError` inside the `async function(recordset)` callback — an unhandled promise rejection that the surrounding `try` (there isn't even a try/catch around this particular `sqlQuery` call) cannot catch. Do not write a scenario asserting a graceful error response for a database failure here; only cover the empty-recordset case (which IS safely reachable via a normal, successful, zero-row query result) and the has-rows case.

Cover: (a) GET /setup with no `id` query param and no prior session vendor code (blank form), (b) GET /setup with no `id` query param but an existing session vendor code from a prior POST /setup (form pre-filled with that code), (c) GET /setup?id=<n> when the lookup returns at least one code row (select-code page rendered with the codes), (d) GET /setup?id=<n> when the lookup returns zero rows (500 "That code didn't look right."), and (e) POST /setup storing the submitted code into the session and rendering the confirmation page. Use the existing tedious mock fixture for the DB-backed GET /setup?id= cases, and a real POST /setup request (via a supertest agent, not fabricated cookie internals) to establish session state for the pre-filled-form case.
