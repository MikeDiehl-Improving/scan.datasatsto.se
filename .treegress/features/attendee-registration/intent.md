Preserve the attendee registration endpoint (`newRegistration` handler in server.js, routes `GET /new/:event` and `GET /new/:event/:id`): it executes the `Scan.New_Identity` stored procedure with the event name and an optional manually-supplied numeric ID (only used when the URL's second segment is present and numeric; otherwise NULL is passed and the database assigns a new ID).

On success (`recordset` truthy), it reads `recordset[0].ID`, ensures `./qr` and `./qr/<event-lowercased>` directories exist, builds `url = https://<host>/<id>`, generates a QR PNG file via `qr.toFile` and a base64 data URL via `qr.toDataURL`, then responds HTTP 200 with JSON `{ id, url, imgsrc, data }` where `imgsrc` is `https://<host>/<event-lowercased>/<id>.png`.

Important existing quirks to preserve exactly (do not invent different behavior):
- If `qr.toFile` errors, respond HTTP 500 with the HTML error page and message "Couldn't create .png file." (no JSON).
- If `qr.toDataURL` errors, respond HTTP 500 with the HTML error page and message "Couldn't create the data blob." (no JSON).
- If `recordset` is falsy (e.g. the stored proc found the request invalid, OR — per the same `sqlQuery` swallowed-error mechanism verified in the `random-scan-lookup`/`batch-random-id-generation` feature — an underlying SQL statement failure also produces a falsy/undefined `recordset` via this same code path), the handler responds HTTP 401 with the HTML error page and message "Invalid ID." There is no reachable path in this handler that produces the generic try/catch's HTTP 500 "There was a problem" response for an async database failure — that catch only guards genuinely synchronous throws before the async SQL call is issued (which don't occur in normal operation), so do not write a scenario asserting a 500 for a database error here.

Route-matching note (verified empirically): the second route is registered as `app.get(/^\/new\/([^\/]+)\/([0-9]*)$/, newRegistration)` — the ID segment regex only matches digits or an empty string. A URL like `/new/techconf/vip` (a non-numeric second segment) does NOT match this route at all (nor any other registered route), so Express falls through to its default 404 handler and `newRegistration` is never invoked — it does NOT reach the handler and auto-assign an ID. Do not write a scenario claiming a non-numeric ID segment produces a successful auto-assigned-ID registration; if you cover this case, assert the plain 404 instead.
